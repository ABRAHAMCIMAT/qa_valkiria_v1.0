# HU-010 y HU-011 — Automatización y bases de datos

## HU-010 — Automatización por lotes

Valkiria genera casos y scripts trazables y los prepara para ejecución controlada.

### Controles

- Máximo 15 casos por lote.
- Frameworks: Selenium, Playwright, RestAssured y Postman-Newman.
- Datos externalizados.
- Page Object Model cuando aplica.
- `case_id` obligatorio y vínculo bidireccional.
- Evidencia por caso.
- Preview y Pull Request; nunca commit directo.
- Playwright en modo preview por defecto.
- Identificación de plataforma, lenguaje y herramienta compatible antes de generar: web/TypeScript/Playwright, móvil/JavaScript/Appium, escritorio/C#/Winium y BD/SQL.
- La matriz de casos manuales puede exportarse a un archivo `.xlsx` sin macros.

`AutomationAgent` prepara casos sin ejecutar el navegador. `PlaywrightRunner` solo se instancia cuando `VALKIRIA_AUTOMATION_EXECUTE=true`; entonces ejecuta los pasos de cada caso web en Chromium contra las pantallas sintéticas, con la misma traducción (`web_steps`) que el código generado.
El endpoint de ejecución no simula resultados: devuelve conflicto si el runner no está habilitado y, al habilitarlo, ejecuta Chromium, captura evidencia por caso y genera un reporte PDF descargable.

## Flujo funcional implementado

1. Generar la HU mediante `/v1/chat` o `/v1/stories`.
2. Evaluarla con INVEST mediante `/v1/stories/{id}/invest`.
3. Generar casos manuales y exportarlos a Excel mediante `/v1/stories/{id}/test-matrix` y `/v1/test-cases/export`.
4. Identificar plataforma, lenguaje y herramientas mediante `/v1/automation/tools/select`.
5. Generar scripts trazables mediante `/v1/automation/batches/generate`.
6. Seleccionar Playwright por defecto para web y rechazar combinaciones incompatibles.
7. Ejecutar el lote mediante `/v1/automation/batches/{id}/execute` cuando el runner esté habilitado.
8. Consultar o descargar la evidencia en `/v1/reports/{id}` y `/v1/reports/{id}/download`.
9. El orquestador selecciona agentes especializados, preserva `trace_id` y registra decisiones y gates.

## HU-011 — Ejecución segura de base de datos

```text
Request sin credenciales
        ↓
Análisis estático
        ↓
DatabaseExecutor
        ↓
SQLite o PostgreSQL sintético
        ↓
Transacción y rollback
        ↓
Reporte, auditoría y métricas
```

### Controles SQL

- `DROP`, `TRUNCATE`, `GRANT`, `REVOKE`, comandos del sistema y cargas peligrosas: bloqueados.
- `UPDATE`, `DELETE`, `INSERT`, `MERGE` y `REPLACE`: requieren controles transaccionales.
- `UPDATE` y `DELETE`: requieren `WHERE`.
- Mutaciones: requieren límite de filas y rollback. El límite se exige en cada `UPDATE` y `DELETE`, no en cualquier sentencia del script.

### Límite de filas en PostgreSQL

PostgreSQL no admite `UPDATE ... LIMIT` ni `DELETE ... LIMIT`. Cuando el motor es PostgreSQL, `application/sql_dialect.py` traduce la forma simple a una subconsulta equivalente sobre `ctid`:

```sql
-- Script aprobado
BEGIN; UPDATE vehicles SET stock = 0 WHERE vehicle_id = 1 LIMIT 1; ROLLBACK;
-- Sentencia ejecutada
UPDATE vehicles SET stock = 0 WHERE ctid IN (SELECT ctid FROM vehicles WHERE vehicle_id = 1 LIMIT 1 FOR UPDATE)
```

- La traducción reutiliza literalmente la asignación y la condición originales, sin normalizar espacios, y bloquea las filas con `FOR UPDATE`.
- El resultado y la evidencia incluyen `dialect_rewrites` con la sentencia original y la ejecutada.
- Solo se traduce `UPDATE <tabla> SET … WHERE … LIMIT n` y `DELETE FROM <tabla> WHERE … LIMIT n`. Si la sentencia tiene alias, `FROM`/`USING`/`JOIN`, `RETURNING`, subconsultas, `WITH`, comentarios o palabras clave repetidas (incluso dentro de literales), el análisis estático la bloquea antes de conectar con el hallazgo `postgresql_limit_requires_simple_form_or_subquery`.
- Alternativa para esos casos: escribir el límite dentro de una subconsulta, que PostgreSQL acepta sin traducción. Por ejemplo, `UPDATE vehicles SET stock = 0 WHERE vehicle_id IN (SELECT vehicle_id FROM vehicles WHERE stock > 0 LIMIT 1)`.
- Producción: siempre bloqueada.

### Contrato de entrada

El cliente envía parámetros de control y el script aprobado. Nunca envía DSN ni credenciales:

```json
{
  "engine": "postgresql",
  "environment": "qa",
  "profile": "synthetic_postgresql",
  "case_id": "HU011-TC-001",
  "script": "SELECT vehicle_id, model FROM vehicles WHERE stock > 0"
}
```

La URL se resuelve desde `VALKIRIA_SYNTHETIC_DATABASE_URL`.

### Evidencia

Cada ejecución conserva estado, motor, `case_id`, `trace_id`, análisis estático, filas, filas afectadas, duración, logs, clave de idempotencia y reporte.

## Fixtures Nissan

Se incluyen vehículos disponibles y agotados, concesionarios activos e inactivos, clientes sintéticos, órdenes aprobadas y canceladas, citas, refacciones y casos de prueba. Todos los datos son ficticios y los correos usan dominios `.test`.

## Estados honestos

- `synthetic_sqlite`: ejecución real contra SQLite en memoria.
- `synthetic_postgresql`: ejecución real contra PostgreSQL sintético.
- `controlled_adapter_boundary`: validación del contrato sin conexión real.

No se debe presentar un estado de preview como ejecución productiva.
